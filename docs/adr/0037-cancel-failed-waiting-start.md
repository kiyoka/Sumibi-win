# ADR 0037: 待機入力の開始失敗と要求IDの後始末

状態：専用waiting-demo・実DLL・非同期workerで実装・検証。Issue #4 / draft PR #10。
[ADR 0035](0035-waiting-demo-and-record-recovery-ui.md)のF7開始処理を補強する。

## 問題

診断DLLがF7要求を開始した直後、EXEのWaiting初期化にはInputWatchの購読、
保護情報の肯定的検査、救済枠の事前確保が必要である。
従来はこの途中で失敗するとWndProcへエラーを返し、開始済みの要求を明示取消しなかった。
また、開始通知が重複した場合は既存Sessionを置き換え、受入れ済みの入力を失う経路があった。

## 契約

開始時にBridgeの要求IDとOwnerの境界epochを捕捉する。
Waiting::beginへ要求IDを渡し、現在のBridge要求と一致することを確認する。
初期化後にも、候補の対象・保護・通知・選択、DLLの保留ID、Bridgeの保留ID、境界epoch、
Ownerの終了状態を照合してからSessionを公開する。

公開前のすべての終了経路は、捕捉した要求IDだけをCancelする。
この取消はworkerへの信号であり、完了の取出しと停止待ちは既存の所有loopに任せる。
途中で別の要求が始まっても、新しい要求をCancel(0)や古いIDの代用で取り消さない。
初期化に失敗したF7は原文を保持し、待機入力の開始失敗をタイトルへ示して次の明示F7を許す。
起動済みのQueueに対する同一IDの重複通知は、既存のSessionと受入れ済み入力を保持する。
未確認救済が残るSessionを、新しいF7の初期化で上書きしない。

診断の初期化失敗は保持中の入力の再送を許さず、workerの遅い応答で古い対象へ書き込まない。
通常デモの結果表示は維持し、waiting-demoではOwnerの開始失敗/救済表示を
Brokerの汎用結果タイトルで上書きしない。

## 検証

Windows 11 x64 build 26300 / 通常ユーザーmedium / Rust 1.99.1。
waiting-demo-testは34件から45件へ拡張した。合成MSG/実DLL・workerを使い、
通常ユーザーのClipboardには書かない。

- 保護拒否（読取専用/非公開）、初期化エラー、初期化中の境界/終了/取消で捕捉IDだけを取消す。
- 古い初期化中に新要求が始まっても、新要求を残す。失敗後の原文・Undo/本文取得を確認する。
- 同一要求の重複通知と未確認救済の上書き拒否。要求がない通知、失敗後の明示再試行も確認する。
- 各ケース終了後、共有救済4枠の再予約、TSF/COM解除とDLLアンロードを確認する。

待機adapter26・救済47・同期入力174・通知30・close4とRust134件・fmt・Clippy 3構成・
build・load_smoke・self/edit/keyを確認した。ログはtarget/issue-4-waiting-start-*.log。
同期入力の最初の連続実行は初回ケースで想定外のSetText回数となり失敗したが、
同じEXE/DLLの単独再実行では174ケースが成功した。原因を確定しておらず、
初回の失敗を成功に読み替えない。
前面化で未通過のwindow/input/delayedの3検査は維持する。
物理打鍵や一般アプリの受付、製品の期限・容量政策は別の受入条件である。
