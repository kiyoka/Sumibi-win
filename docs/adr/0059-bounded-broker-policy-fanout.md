# ADR 0059: 複数Broker接続への有限な政策通知

2026-10-25 / Issue #4 / PR #10。

製品Brokerが複数の認証済みclientへ設定・認可変更を配る際、変更ごとに
無制限の通知を積むと容量と失効の順序が曖昧になる。OS非依存の
`PolicyFanout`を`sumibi-protocol`へ追加し、接続を最大8件、各接続の
未配送`PolicyChanged`を最大1件に制限した。

接続追加はOS peer認証後に行い、その時点のpolicyでHello/Readyを作る。
初期フレームの形式・型・broker IDを接続一覧との照合より先に検証し、
不正なHelloで既存session IDの状態を探れないようにする。
Readyの完全な書込後に`ready_delivered`を呼ぶまで、その接続のConvertや
政策通知の配送確認は拒否して接続を退役させる。Readyと直後の政策通知を
同じpipe書込にまとめた場合も、書込完了後にReady、政策通知の順で確認する。
通常の通知取得はReady書込中の接続を除外する。Ready完了後に再度取得する。
同一書込にまとめる場合だけ`coalesced_ready_notice`で先に取得する。
同時に生きている2接続が同じsession IDを主張した場合は後からの接続を拒否する。
接続keyはBroker寿命中に単調増加させ、切断後も再利用しない。古い書込完了が
新しい接続へ届くことを防ぐ。
切断後の正規再接続には同じclient寿命IDと新しい世代を使える。
古い世代のHelloは拒否する。Broker寿命中の接続追加は暫定64件を上限とし、
履歴を捨てて旧世代を受け付ける代わりにBrokerを退役させる。新しいBrokerは
新しいboot IDを使用する。製品の寿命・再起動方針は複数client実I/O時に確定する。
同じclient寿命IDの最後に受け付けた要求番号も履歴へ保持し、新世代の
`BrokerSession`へ引き継ぐ。世代を進めても旧要求番号の再利用は拒否する。
政策の版または許可の巻き戻りは全体を変更せず拒否する。正常な更新は
全接続の`BrokerSession`へ適用し、保留中の変換を取消して通知を保持する。
通知の完全な書込後にだけ配送を確認し、次の要求を許す。二度目の更新時に
前の通知が未配送なら、その接続を退役させ、呼出し側へ閉鎖すべき接続IDを
返す。残る接続と後から加わる接続は最新policyを使う。これにより、
遅いclient一つが他の接続の更新を妨げない。
未配送通知は最大8件の所有コピーとして一度だけ取り出せる。取り出し済みの
通知は再度返さず、書込完了確認も取り出し済みの通知だけに許す。
予約を迂回して同じ通知を参照できる公開照会APIは置かない。
通信担当はFanoutのlockを離してから各pipeへ書き込み、完了時に接続keyと
通知の版を照合する。書込失敗では接続を閉じる。
要求期限の処理も接続keyで限定する。`expire`は期限を過ぎた保留要求だけを
除去し、遅れたworker結果を配送しない。他の接続の保留要求と接続状態には
影響しない。`expire`後にはその要求のTimeout frameも作れない。
worker完了がtimerの`expire`より先に届いても、期限を越えた成功結果や
Timeout以外の固定エラーは破棄し、その接続は次の要求に再利用できる。
Timeoutを返す場合は期限時に先に`error(..., Timeout, ...)`を呼ぶ。
呼出し側がタイマー、応答の書込、または切断を担当する。
書込完了の確認には接続IDと配送したpolicyを渡す。古い書込完了が次の通知に
遅れて到着した場合や同じ完了が重複した場合、その接続を退役させ、
新しい通知を誤って配送済みにしない。

単体検査では、2接続への失効、保留要求の取消、追加接続の新policy、
8件上限、寿命64接続と旧世代Hello・旧要求番号の拒否、
不正初期フレームの優先拒否、
Ready書込前の要求・通知確認の拒否、
同時session ID重複、
遅い接続と古い書込完了だけの退役、
接続単位の期限切れと遅延結果の破棄、
ClientSessionと実際の版付きフレームを往復させた再接続後の要求番号継続、
不正更新の原子的拒否を確認する。
Ready書込中の通知が通常の書込担当へ渡らず、Ready完了後または明示的な
同一書込で一度だけ取得できることも確認する。
Hostの`PolicyAuthority`変更を2件のProtocol接続へ渡す結合検査では、
保留中と待機中の両方が失効通知を受け、古い結果が公開されないことを確認する。
この型はI/O、OS peer認証、UI操作、別process間の設定変更伝達を持たない。
診断用Brokerの単一Channelはこのfanoutを1接続として使う。実子Brokerの
既存回帰はその1接続の通知・結果順序を確認する。後続の
[ADR 0061](0061-two-client-broker-pipe-diagnostic.md)では一つの親processから
2本のpipeを開く診断を追加した。製品の複数client実I/O配信は未実装。
製品統合では、返された退役IDのpipeを確実に閉じ、
配送失敗も同様に退役させ、所有側の適用前policy再検査と結ぶ必要がある。
