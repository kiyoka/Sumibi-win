# ADR 0049: Host内の設定・認可スナップショット

2026-10-25 / Issue #4 / PR #10。

ADR 0047の`PolicySource`に対して、Host内メモリーだけの`PolicyAuthority`を追加した。
初期状態は設定版1・認可版1、送信禁止、同意なし、キーなし。
接続先変更では設定版と認可版を、キーの交換・削除、同意付与・取消では認可版を進める。
変更を単一のlock内で公開するため、workerは接続先・同意・キー・版が混ざった
途中状態を受け取らない。版が上限に達した場合やlockが利用不能な場合は変更を拒否し、
送信ゲートのスナップショット取得も失敗にする。

接続先またはキーを変更すると手動同意を解除する。新しい接続先への同意を旧版から
引き継がず、同じ文字列のキーへの交換でも認可版を進める。同意付与は、指定した
接続先が現在の接続先と一致し、キーが存在するときだけ成功する。
模擬Transportと結合したテストで、同意前の拒否、変更後の旧要求拒否、
送信中の同意取消による旧結果破棄を確認した。ADR 0048のloopback HTTP検査も
この政策状態を通して送信する。

追補: IPCへ渡す設定版・認可版・許可状態だけの`wire_policy`と、前回公開版から
変化した場合に最新版を返す`wire_change_after`を追加した。変更通知は有限の
1スナップショットへまとめられる。カーソルが現在より進んでいる場合と、
設定版だけが遅れたカーソルも変更通知として返す。型付きProtocolの
`Ready`→`Convert`→`PolicyChanged`→旧`Result`へ接続した検査で、
保留要求の取消、次要求の拒否、旧結果の無視を確認した。取消後に再同意して
最終状態が許可へ戻る場合も、新しい認可版の通知で旧保留要求を取り消す。

この型は設定UI、永続JSON、Credential Manager、Brokerへの実プロセス間
`PolicyChanged`配送の実装ではない。配送側は新しい政策を要求受付前に送信し、
送信不能時にはその接続を閉じる必要がある。将来のUI操作は保存・発行順序を決め、
同意の明示操作を呼ぶ必要がある。
送信を開始した後の本文は取消で回収できない。政策変更と送信開始の競合、
全DLLへの失効配送は製品接続前に別途検証する。
