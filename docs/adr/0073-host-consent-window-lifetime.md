# ADR 0073: 送信管理画面と明示起動Hostの寿命

## 起動と現在の範囲

`sumibi-host host-window [absolute-settings-path]`で送信管理画面を起動する。
パスを省略した場合は既存のLocalAppData配下の設定を読む。
初回設定の作成とキー操作は既存のsettings-init・settings-windowを使う。

画面threadはWindowsメッセージ処理に専念し、`HostControl`のowner threadが
保存設定の検証、Credential Manager読取、非公開Brokerの生成と同意配信を行う。
起動時は既存方針どおり未同意で、キーを表示・ログ出力しない。
画面は完全な接続先、モデル、キー有無を表示し、「入力アプリとの接続は準備中」と明示する。

この起動経路はランダムなBroker名を公開せず、peerを受付せず、変換dispatchも行わない。
peerの信頼できる発見と起動元の保護を後続で実装するまで、PIDやpipe名を入力して
接続する代替経路は設けない。既存のnative変換入口は別のBroker試験で検証している。
単一起動管理は[ADR 0074](0074-logon-scoped-host-instance.md)へ続く。
Windows自動起動や通知領域への格納は今回の範囲に含めない。

## 同意操作と表示

UIは版付きのofferを表示してから、そのofferを許可要求に渡す。
完全な接続先とモデル、送信対象が入力本文とAPIキーであることを確認画面にも表示し、
「いいえ」を既定にする。キーがない場合、処理中や終了中は許可を無効にする。
同意はこのHostの起動中だけで、保存しない。キーの変更後はHostを開き直す。

command queueは1件で、別のatomicな受付枠により同意操作は同時1件とする。
ownerはConsentTaskを開始し、完了receiptを同一Brokerで配信・終了確認する。
確認が期限切れならreceiptを保持して再試行する。完了前にはReadyへ戻さない。
古いofferや別authorityのofferは拒否し、新しい表示と固定エラーを返す。
画面の状態取得もtry_lockを使い、送信やpolicy更新のlockを待たない。

## 終了

×と「Hostを終了」はウィンドウを即座に破棄せず、独立した終了flagを立てる。
command queueが満杯でも終了要求を失わず、それ以降の新規操作を拒否する。
ownerはBrokerを先にretireし、まだ受付けていない許可要求を破棄する。
進行中のConsentTaskは完了まで保持し、その後に最後の取消taskを実行する。
これにより、閉じる直前の許可が遅れて成立しても、終了時の取消が後になる。
取消とBroker資源の終了を確認してからownerを終了する。各retire試行の期限は25msで、
未完了のbootを保持して後から再試行する。資格情報読取などOS処理自体に固定終了時間を
保証するものではなく、その待機中もUIメッセージは処理する。

UIはownerのJoinHandleが終了済みの場合だけjoinし、その後にネイティブ画面を破棄する。
メッセージloopが終了・失敗した場合も終了flagを立て、ownerの完了をpollする。
controllerのDropは終了を要求するがjoinしないため、通常のUI終了経路では必ず完了を待つ。
起動・継続・取消に失敗した場合は成功として報告しない。

## 検証

合成キーのauthorityと実Brokerで許可・取消、古い/異なるauthorityの拒否、
起動途中の終了とqueue内の許可破棄を検査した。
送信guardで許可workerを待たせた状態でも状態poll・終了要求が進み、guard解放後の
遅い許可を最後に取り消して終了することを確認した。
起動失敗はFailedと固定エラーで取得できる。

試験用設定の実画面で接続先・モデル・キー欠損表示、許可ボタンの無効化、×での
終了コード0を確認した。画面からの許可やキー操作は行っていない。
外部API、証明書store、既存設定、保存済みキーと機械登録は変更していない。
正常TLS通信と一般アプリの変換成功は、この検査の対象ではない。
