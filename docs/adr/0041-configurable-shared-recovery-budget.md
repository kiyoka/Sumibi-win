# ADR 0041: 件数と本文総量を同時に予約する共有救済予算

状態：Coreと既存の専用EXE経路で実装・検証。Issue #4 / draft PR #10。
[ADR 0021](0021-shared-input-recovery-budget.md)の共有4枠を、製品の容量検討にも使える有限な予算へ拡張する。

## 問題

従来のBudgetはレコード件数だけを数え、本文総量4096 UTF-16単位は
「4件 × 1件1024単位」の結果として成立していた。件数を増やすと、
この暗黙の本文上限も増える。件数と本文量を別々の原子変数で予約すると、
二つ目の取得に失敗した間に他の所有者と競合し、消費前の確定した予約を示しにくい。

## 決定

`Budget::with_limits(max_records, max_text_units)`で、1〜1024件・1〜16384 UTF-16単位の
有限なプールを作れるようにする。既定のBudgetは従来どおり4件・4096単位とする。
予約中、確認待ち、本文除去済みのレコードは、その元の件数と最大本文長を占有する。
BackspaceやEnterなど本文を持たない操作も1件を占有する。

件数と本文単位数を一つの64-bit原子状態の上位/下位32-bitへ格納し、
両方の上限を確認してから一度のcompare-exchangeで予約する。
失敗時にticketと既存レコードは変えない。Permitは予約した本文単位数を保持し、
破棄・明示確認・期限切れ・所有者Dropのどの経路でも両方の容量を一度だけ返す。
予算自体は本文、COM参照、callbackを保持しない。

プールのcloneを渡した所有者だけが容量を共有する。別のプールや別プロセスには及ばない。
このAPIは製品の容量値やプロセス間の予約方法をまだ決定せず、製品キーも有効化しない。
製品経路を接続する前に、全対象で共有する予算の所有者、超過時の通常入力への切替、
救済期限と確認UIを決める必要がある。

## 検証

Coreに2件追加して96件、workspace合計136件。本文上限と件数上限の独立した拒否、
本文なし操作の件数占有、本文除去中の容量保持、破棄後の再予約、8 thread競合時の
本文総量上限を確認した。初回の実DLL回帰では救済47・待機adapter26・待機デモ57ケースが成功し、
TSF/COM解除とDLLアンロードも確認した。fmt・Clippy 3構成・spike buildも成功した。
ログは`target/issue-4-recovery-budget-*.log`。

続く実DLLの救済入力ケースでは、本文を持つ1件と本文なしの1件を保持して本文総量2単位を満たし、
残る件数枠でも文字入力を消費前に拒否して、通常ホストで1回だけ入力することを確認した。
既存レコードを破棄すると次の入力がDLL取引へ進み、失敗時の供給文字だけを救済した。
既存本文・Undo・追加の本文取得とDLL書込回数を照合した。
ログは`target/issue-4-text-budget-recovery-input-test.log`。

`window-test`は文書関連付け、下線、取消、専用ホストUndoまで通過したが、
Windowsが診断ウィンドウの前面化を拒否し、実TSFキー配送では未通過のままである
（`target/issue-4-current-window-test.log`）。このCore変更を実打鍵・一般アプリの
標準Undoや製品のプロセス間容量の受入れとは扱わない。
